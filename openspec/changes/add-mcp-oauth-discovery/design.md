## Context

- `/mcp` is a REST API route (`POST`, `COGNITO_USER_POOLS` authorizer) in front of
  the `mcp` Lambda, on the default `execute-api` domain under a stage path
  (`/prod`). The authorizer's `401` is generated by API Gateway: body
  `{"message":"Unauthorized"}`, no `WWW-Authenticate`.
- The user owns a Route53 hosted zone, so a custom domain is available.
- The authorizer has no OAuth scope configured, so it accepts **ID tokens** only.
  `authInfoFromClaims` already handles access-token claims (`client_id`, no `aud`).
- The user pool is Google-only (Managed Login). The `draupnir-app` app client is
  Pulumi-managed with fixed callback URLs and `ALLOW_REFRESH_TOKEN_AUTH`; the
  Google identity provider, the pre-sign-up trigger and the Managed Login domain
  are pool-level, so any app client on the pool inherits them.
- What an MCP client does (spec revision 2026-07-28, read from the official
  pages): on `401` it uses `resource_metadata` from `WWW-Authenticate`, else
  probes the path-suffixed then root `/.well-known/oauth-protected-resource`; it
  reads `authorization_servers`, then discovery metadata (RFC 8414 or OIDC; for
  an issuer with a path, three URLs in order, the third being
  `<issuer>/.well-known/openid-configuration`); it needs `S256` in
  `code_challenge_methods_supported`; it registers through pre-registration,
  CIMD (`client_id_metadata_document_supported`), DCR (`registration_endpoint`),
  or else prompts the user; it MUST send `resource` even if unsupported; it
  validates RFC 9207 `iss` only if present or advertised.
- Cognito (per ADR-0002 and public reports, not verified against AWS docs): no
  DCR, no confirmed CIMD, ignores `resource`, access tokens carry `client_id`
  and `scope` but no `aud`, callback URLs are listed explicitly.

## Goals / Non-Goals

**Goals:**
- A client connects from only the MCP URL, with a Google sign-in and no manual
  client ID or token, including clients that probe only well-known paths at the
  origin root.
- No change to how the data tools run (still `sub` from the authorizer claim).

**Non-Goals:**
- A full OAuth proxy (own authorize/callback/token handling), CIMD, token
  audience binding, or changes to the primary app API.

## Decisions

### 1. One small unauthenticated Lambda, not an OAuth proxy

A new Lambda behind three unauthenticated routes on the existing MCP REST API:
`GET /.well-known/oauth-protected-resource`, `GET /.well-known/openid-configuration`,
`POST /register`. Authorize and token requests go **directly to Cognito's Managed
Login domain**; the shim never sees a code or token.

- Alternative, a full proxy (own `/authorize`, `/callback`, `/token`): handles any
  redirect URI and `resource`, but holds the authorization state and token
  exchange, which is the highest-risk code in the system. Not needed if decisions
  4 and 6 hold.
- Alternative, metadata only with a manual client ID: breaks for clients whose
  callback port is random and for claude.ai's fixed callback unless the user
  edits the app client by hand.

### 2. A custom domain, so the issuer is the origin and well-known paths are at the root

- Hostname `mcp.draupnir.nodm.name` in the `nodm.name` Route53 zone (both Pulumi
  config). A dedicated subdomain keeps the origin's root well-known paths for MCP
  alone and leaves `draupnir.nodm.name` free for a later app. Alternatives
  considered: `draupnir.nodm.name/mcp` (shared origin, later collisions on root
  well-known paths) and `nodm.name/draupnir/mcp` (issuer with a path, metadata on
  the apex domain).
- A regional API Gateway custom domain `<mcpHost>` (Pulumi config), an ACM
  certificate in the same region validated by a DNS record in the Route53 hosted
  zone (config), a base path mapping of the empty path to the `mcp` stage, and an
  alias A record. The MCP URL is `https://<mcpHost>/mcp`; the issuer is
  `https://<mcpHost>` (no path).
- Discovery then follows the plain forms: `/.well-known/oauth-protected-resource/mcp`
  and the root form, and `/.well-known/oauth-authorization-server` then
  `/.well-known/openid-configuration` at the root. The shim serves all of them,
  and the `401` challenge still names the exact URL.
- The `execute-api` default endpoint stays enabled, so existing checks keep their
  host. Its tokens work, but its metadata names the custom domain.
- Alternative, no custom domain: the stage prefix makes root-level well-known paths
  unroutable, so clients that skip the challenge could not discover anything
  and the issuer would be tied to the stage URL.

### 3. The challenge comes from a gateway response

An `aws.apigateway.Response` of type `UNAUTHORIZED` sets
`gatewayresponse.header.WWW-Authenticate` to
`Bearer resource_metadata="https://<mcpHost>/.well-known/oauth-protected-resource/mcp"`
(static, deploy-time URL).
No Lambda is involved, so it also covers requests the authorizer rejects before
any code runs.

### 4. Access tokens, via an OAuth scope on the `/mcp` method

Set `authorizationScopes: ['openid']` on the `/mcp` method. A
`COGNITO_USER_POOLS` authorizer with scopes expects an access token and checks the
token's `scope`; without scopes it expects an ID token. MCP clients send the
access token, so the method must change. Effect: the manual ID-token flow used for
checks stops working (**BREAKING**, recorded in the proposal and spec).

- Alternative, a Lambda authorizer accepting both token types: more code to
  secure and no benefit for real clients. It is the fallback if the scope
  approach fails (task 3.2).
- Claims injected for an access token include `sub` and `client_id`;
  `authInfoFromClaims` already falls back to `client_id`.

### 5. `/register` creates one public app client per redirect-URI set

`POST /register` validates the body, then calls Cognito:

- Name `mcp-dcr-<first 16 hex of sha256 of the sorted, joined redirect URIs>`.
  `ListUserPoolClients` finds an existing client with that name and returns its
  id (idempotent); otherwise `CreateUserPoolClient` creates it. The mapping from
  the response to `client_id` and `redirect_uris` follows RFC 7591;
  `token_endpoint_auth_method` is `none`, `grant_types` `authorization_code`.
- Client settings: no secret; authorization code flow; scopes `openid email profile`;
  supported identity providers `Google` only; `ExplicitAuthFlows` as the existing
  app client (`ALLOW_REFRESH_TOKEN_AUTH`); callback URLs exactly the requested
  ones; logout URLs none.
- Allowlist (constants in code): the claude.ai and claude.com MCP callbacks, and
  `http://localhost:<port>/<path>` and `http://127.0.0.1:<port>/<path>`. Anything
  else, a missing `redirect_uris`, or more than 5 URIs is `400`
  (`invalid_redirect_uri` or `invalid_client_metadata`).
- Cap: if the count of `mcp-dcr-` clients is at least 25 and the set is new,
  respond `429`/`temporarily_unavailable` instead of creating.
- A new app client is unusable in Managed Login until a branding style is attached
  (`infra/lib/cognito.ts` notes this), so `/register` also calls
  `CreateManagedLoginBranding` (Cognito-provided values) for the new client, and
  deletes the client if that fails so no half-working client takes a cap slot.
- IAM: `cognito-idp:CreateUserPoolClient`, `ListUserPoolClients`,
  `CreateManagedLoginBranding` and `DeleteUserPoolClient` on the user pool ARN only. The code is the gate for an unauthenticated caller,
  so the allowlist and cap are tested as security requirements.
- Alternative, one static app client with every callback pre-registered: cannot
  cover loopback ports a client picks at random.

Concurrent first registrations of the same set can create two clients; both
work and only waste cap slots. Accepted; throttling (decision 7) keeps it rare.

### 6. `resource` and token audience

The user pool ignores `resource`, so tokens cannot be bound to the MCP server and
the endpoint cannot do the audience check the spec asks for. Compensating
controls: signature, issuer, scope (decision 4); sign-up to the pool is
restricted by the pre-sign-up email allowlist (ADR-0002), and every tool runs as
the caller's `sub` under row-level security, so a token can only ever read what
its own user may see. This is a recorded deviation (ADR), not a
silent skip. Verified on prod (task 3.3): Cognito accepts `resource` on
`/oauth2/authorize` but then issues a code that `/oauth2/token` cannot redeem
(`invalid_grant`, with or without `resource` on the token request). With no
`resource` on authorize the flow works. So the shim adds `GET /authorize`, a
`302` to Cognito's authorize endpoint with `resource` removed, and a
form-forwarding `POST /token` that also strips `resource` (so clients may send it
on both, as the spec requires), forwards `authorization_code` and `refresh_token`
grants, relays the response, and logs nothing (the body carries codes and tokens).
The metadata's `authorization_endpoint` and `token_endpoint` name the shim. The forwarder holds no
state, is throttled, and never sees a client secret (public clients only).

### 7. Throttling

Stage method settings on `POST /register`: low rate and burst (1 rps, burst 5)
and the Lambda timeout kept short. Metadata routes use the stage defaults.

### 8. RFC 9207 `iss`

Cognito's authorization responses carry no `iss`, and the metadata does not
advertise `authorization_response_iss_parameter_supported`, so a client following
the 2026-07-28 decision table proceeds. The spec notes a future revision may make
`iss` mandatory; that would need a proxy (decision 1's rejected alternative). Noted
in the ADR.

### 9. Placement

The Lambda is a second entry point of the `mcp` project (`oauth` handler) with
its own IAM role and environment: `COGNITO_USER_POOL_ID`, the Managed Login base
URL, and the MCP origin (`https://<mcpHost>`). `mcp/src/lib/mcp.ts` and `/mcp` are untouched.

## Risks / Trade-offs

- **Cognito may reject `http://127.0.0.1:<port>` callbacks** (one source says it
  blocks that form) → the registration spike (3.1) checks both hosts; if only
  `localhost` is accepted, the endpoint registers `localhost` for loopback
  requests and the client's redirect still matches only if it uses `localhost`;
  document the limit.
- **App clients created outside Pulumi** drift from the stack → fixed name prefix,
  a cap, and a documented cleanup (`list-user-pool-clients` by prefix).
- **Switching the method to access tokens breaks the ID-token flow** → documented;
  the e2e task uses an access token; rollback is a revert and deploy.
- **Custom domain setup** (certificate validation delay, DNS propagation) → the
  default endpoint stays up meanwhile; validation is declarative in Pulumi.
- **An unauthenticated endpoint can create resources** → allowlist, cap,
  throttle, narrow IAM, tests.
- **Callback URLs for Claude clients differ across sources** (`/api/mcp/auth_callback`
  on claude.ai and claude.com; one report cites `/oauth/callback`) → the allowlist is
  one constant confirmed against Anthropic's docs and a live attempt (task 4.1).
- **The 29s API Gateway ceiling and cold starts** are not a concern for these
  small routes.

## Migration Plan

- Deploy adds the custom domain and DNS records, the Lambda, routes, gateway
  response and throttling; the `/mcp`
  method change takes effect in the same deploy (ID tokens stop working).
- Rollback: revert and redeploy; delete leftover `mcp-dcr-` app clients if wanted
  (the same revert removes the custom domain and records).
  No schema or data change.
